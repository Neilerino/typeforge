Lesson 0002 · Collaborating with an agent

Riff broadly. Commit narrowly.

Move from user need to rules, responsibilities, and a stable module seam—then select one tracer example and let its test pull the minimum data and logic into existence.

Verdict

Your proposed structure is good. Make it iterative, split domain facts from code definitions, and put an explicit confirmation gate before the first test.

10 minutes one reusable prompt vertical slices
The adjustment

Use two loops, not one long handoff.

A large up-front pass from needs through every test invites imagined behavior and premature structure. Discovery can range broadly; delivery should advance through one behavior at a time.

Discovery loop · revise freely

Clarify the promise

  1. User outcome and constraints
  2. Rules, examples, counterexamples
  3. Domain terms and invariants
  4. Module responsibility and interface options
Delivery loop · one slice

Make one promise true

  1. Agree the seam and one tracer example
  2. Write one unmarked failing test
  3. Implement the minimum behavior
  4. Review structure, record learning, repeat
Use xfail only when you are parking an accepted contract.

If the agent will implement the test immediately, leave it genuinely red. If you need to merge or preserve the contract before implementation, first verify the failure, then add a strict marker with a capability-based reason.

The conversation funnel

Six phases, each ending in a decision.

01 · FRAME

Value

Who needs what change, why now, what proves success, and what is explicitly out of scope?

02 · DISCOVER

Rules

Concrete examples, counterexamples, failure cases, invariants, and unresolved questions.

03 · MODEL

Language

Name domain facts precisely. Do not turn every noun into a class.

04 · DESIGN

Responsibility

Which module owns the decision? Compare two interface and seam shapes for depth and locality.

05 · SELECT

Tracer

Choose one representative example and only the interface data needed to express it.

06 · DELIVER

Evidence

One failing test, minimum behavior, green check, structural review, then the next example.

The agent should show its work at each gate:

Decisions, assumptions, open questions, and proposed artifacts. You confirm the seam before code. If a test reveals ambiguity, return to discovery instead of forcing the current design through.

Worked Typeforge session

“Never publish an incomplete interface.”

This is the implemented contract from the compiler pipeline tests, reconstructed as if you and an agent were discovering it.

User need
A library author must be able to trust a generated stub as the complete public interface.
Rule
If Typeforge cannot safely preserve a public declaration, generation fails instead of silently omitting it.
Examples
A top-level while statement is rejected. A runtime call expression and code under if __name__ == "__main__" are ignored because they do not define the interface.
Responsibilities
The module-surface implementation classifies public declarations; the compiler pipeline composes the stages and returns the typed failure.
Agreed seam
generate_module(path, maximum_arity) -> Result[GeneratedModule, GenerationError]. Test through this interface, not a private classifier helper.
Interface data
UnsupportedPublicDeclaration crosses the seam and reports authored source location. No new internal record is required by the contract.
Tracer test

Reusable handoff

Start an agent session with this.

Replace the bracketed text. The gates keep the agent collaborative during discovery and narrow during delivery.

SPECIFICATION SESSION PROMPTTypeforge
Help me discover and deliver a specification for [feature idea].

Start by reading AGENTS.md, DESIGN.md, and the nearest existing tests. Do not
write implementation code yet.

Work with me through these phases:

1. Frame the user or business outcome, success signal, constraints, and non-goals.
2. Elicit rules using concrete examples, counterexamples, failures, and edge cases.
3. Sharpen Typeforge-specific terms and separate domain facts from code structures.
4. Assign each decision to the module that should own it. Propose two plausible
   interface/seam designs and compare their depth, leverage, and locality.
5. Recommend the smallest representative tracer example. Identify only the
   interface data definitions needed to express that example.

At the end of each phase, show:
- decisions we have made;
- assumptions you are making;
- open questions;
- artifacts that would need updating.

Pause for my confirmation before choosing the seam or writing tests.

After I confirm, state the exact pre-agreed seam and observable outcome. Write one
unmarked failing test through that interface, plus only the interface data needed
to express it. Run the test and verify it fails at the behavior assertion for the
expected reason.

If we are implementing immediately, leave the test red and write the minimum code
to pass it. If we are deliberately deferring implementation, add strict=True with
a capability-based xfail reason. Do not create a batch of future xfail tests.

Once the slice passes, review the structure and update the specification artifacts
with anything the slice taught us. Then propose—but do not pre-implement—the next
tracer example.

No repository changes are implied until you confirm the seam.

A useful session ends with fewer unknowns, not necessarily more files.

Keep business rules and unresolved questions in a small feature note; domain vocabulary in a glossary only when terms crystallize; hard-to-reverse architecture decisions in an ADR only when a real trade-off was chosen; executable outcomes in tests; and implementation data beside the module that owns it.

Grounded in discovery, formulation, and automation, Typeforge's design principles, and the course's specification-first reference.

Ask your agent—or this one—to challenge the next real feature with this workflow. Explaining why you chose the seam is the next retrieval exercise.
