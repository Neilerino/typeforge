Lesson 0001 · Specification-first Typeforge

Make the promise before the machinery.

Use examples to define what a Typeforge feature means, strict xfail to keep an agreed promise visible, and TDD to make one promise true at a time.

8 minutes one boundary decision one contract draft
The mental model

Your idea is sound—with one important separation.

Specification by example, TDD, and xfail solve different problems. Keeping their jobs distinct prevents a backlog of expected failures from becoming a vague substitute for design.

What Specification by example

Turns a rule into concrete, reviewable observations at a named system boundary.

How Test-driven development

Selects the next example, sees it fail, makes it pass, then improves the design.

State Strict expected failure

Keeps an agreed but unfinished contract in the suite and makes accidental success visible.

xfail is not the red step.

A normal strict-XFAIL lets the overall suite remain green. Run the selected contract with --runxfail to expose its genuine failure while implementing it. When it passes, strict XPASS deliberately fails the suite until you remove the marker.

  1. 01 · DISCOVERName the rule

    Find examples, edges, and questions before choosing code structure.

  2. 02 · SPECIFYChoose a boundary

    Assert only what a caller or neighboring subsystem can observe.

  3. 03 · PARKConfirm, then xfail

    First see the right failure. Add a strict marker with a capability-based reason.

  4. 04 · DRIVEExpose red

    Use --runxfail; implement the smallest vertical slice; keep feedback tight.

  5. 05 · RATCHETRemove and refactor

    Strict XPASS signals completion. Remove the marker, stay green, improve structure.

Specify at the narrowest stable seam that owns the promise.

“Specification-based” does not mean every test must be end-to-end. It means the chosen system and its observable outcome are explicit. Typeforge already has four useful system boundaries.

Prefer capability reasons.

reason="Input maps cannot yet produce a shared DeferredMap" says what is missing. reason="TODO" or reason="not implemented" cannot help you decide whether the contract is still valid.

Before adding @pytest.mark.xfail:

Make the executable test fail at its final observation for the missing capability. A NameError, placeholder assertion, broken fixture, or wrong exception proves only that the test is broken. If one specific exception represents the unfinished behavior, add raises=ThatException so unrelated failures stay red.

Finish and retain

The workflow in four commands.

# 1. Prove the marked contract really fails for the intended reason
uv run pytest path/to/test.py::test_contract --runxfail -q

# 2. Drive the slice while keeping the failure visible
uv run pytest path/to/test.py::test_contract --runxfail -q

# 3. After implementation, strict XPASS tells you to remove the marker
uv run pytest path/to/test.py::test_contract -q

# 4. With the marker removed, validate the affected seam
make check path/to/test.py path/to/relevant_source.py
