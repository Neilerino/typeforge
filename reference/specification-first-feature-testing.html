Specification-first feature testing

The short version

Specify the promise at a stable boundary. Prove the test fails for that missing promise. Park it with strict xfail. Expose red with --runxfail. Remove the marker when it passes.

Keep the roles separate

What / how / state

SpecificationWhat observable behavior means.
TDDHow the next behavior drives design.
Strict xfailWhether an agreed contract is still pending.
Recipe

From idea to regression

  1. Name the system. Which boundary owns this promise?
  2. State one rule. Include examples, edges, and open questions.
  3. Choose an observation. Output, typed failure, diagnostic, or import graph.
  4. Write one test. See it fail at the final assertion for the right reason.
  5. Park deliberately. Add strict=True and a capability reason.
  6. Drive with red visible. Use --runxfail; implement the smallest slice.
  7. Ratchet. Let strict XPASS fail, remove the marker, refactor while green.

Readiness check

Before marking xfail

  • The rule is agreed, not speculative.
  • The system boundary is named.
  • The outcome is observable at that boundary.
  • The failure reaches the final behavior assertion.
  • The reason describes a missing capability.
  • The slice fits one short TDD loop.
  • raises=... narrows the expected failure when useful.
Failure modes

Three ways the practice goes stale

TODO cemetery

Broad, non-strict xfails hide accidental completion and say nothing about priority or capability.

Design handcuffs

Call counts, private helpers, and internal object choreography turn today’s design into tomorrow’s false contract.

Example tunnel vision

A few examples cannot prove a general rule. Add explicit invariants or property tests where the promise is universal.
